## 2. Reglas de negocio

- **Acceso institucional (RN-01):** el registro acepta exclusivamente correos
  terminados en `@unisimon.edu.co`.
- **Verificación dual (RN-02):** las cuentas se pueden crear sin verificación,
  y por decisión temporal se permite publicar y alquilar aunque correo y
  WhatsApp aparezcan como “Sin verificar”. Los proveedores de envío todavía
  no están configurados; la restricción de uso se podrá activar cuando lo
  estén.
- **Disponibilidad en campus (RN-03):** para publicar, el prestador configura
  al menos una franja semanal. Cada reserva debe estar completamente dentro de
  las franjas del propietario, en horario `America/Bogota`.
- **Comisión UniTrade (RN-08):** 12% del subtotal del alquiler.
- **Moneda:** pesos colombianos (COP) como enteros; no se usan decimales.
- **Quién paga qué:**
  - El arrendatario paga el **subtotal**.
  - UniTrade retiene la **comisión**.
  - El propietario recibe en su billetera **subtotal − comisión**.
- **Cálculo en servidor:** el backend nunca confía en montos enviados por el
  cliente. Si se paga una reserva existente, usa el subtotal guardado en la
  base; si se crea la reserva en el checkout, usa `tarifaHora × horas`.
- **Redondeo:** `comision = round(subtotal × 0.12)` y siempre se cumple
  `comision + montoPropietario = subtotal`.
- **Idempotencia:** una reserva no se cobra dos veces y el header
  `Idempotency-Key` permite reintentos seguros.

### Validación presencial y mora (RN-10, RN-11 y RN-12)

- La entrega y la devolución se confirman presencialmente desde la cuenta del
  propietario. El arrendatario muestra un PIN de 4 dígitos o un QR distinto
  para cada etapa; el código solo se entrega al arrendatario después del pago.
- Después de los 15 minutos de gracia desde el fin de la reserva, se cobra una
  hora adicional por cada hora o fracción de retraso, según la tarifa del
  artículo. El recargo se actualiza automáticamente cada minuto.
- Al confirmar la devolución, el recargo se debita primero de la billetera del
  arrendatario si tiene saldo suficiente. Si no, queda pendiente para pagarlo
  desde “Mis Alquileres” mediante checkout.
- Cuando la devolución supera las dos horas de retraso, el arrendatario no
  puede crear nuevas reservas hasta devolver el artículo y pagar los recargos
  pendientes.

Endpoints de certificación física y pago de mora:

| Método | Ruta | Descripción |
|---|---|---|
| `POST` | `/api/reservas/articulos/:articuloId/entrega` | Confirma la entrega con PIN o QR |
| `POST` | `/api/reservas/articulos/:articuloId/devolucion` | Confirma la devolución y liquida la mora |
| `POST` | `/api/reservas/:id/pagar-mora` | Paga por checkout un recargo pendiente |

### Ejemplo de desglose

Reserva de 4 horas a $15.000/hora:

| Concepto | Valor |
|---|---:|
| Subtotal | $60.000 |
| Comisión UniTrade (12%) | $7.200 |
| Total que paga el arrendatario | $60.000 |
| Abono a la billetera del propietario | $52.800 |

## 3. Modelo de datos

Migración: `prisma/migrations/20261021180000_pagos_billetera_hu06_hu10`.

### `pago`

| Campo | Tipo | Uso |
|---|---|---|
| `alquilerId` | `String @unique` | Una reserva tiene un solo pago |
| `monto` | `Int` | Total cobrado al arrendatario |
| `comision` | `Int` | Retención de la plataforma |
| `montoPropietario` | `Int` | Abono al propietario |
| `moneda` | `String` | COP por defecto |
| `estado` | `EstadoPago` | PENDIENTE / PROCESANDO / COMPLETADO / FALLIDO / REEMBOLSADO |
| `idTransaccion` | `String? @unique` | Id de la pasarela (`sbx_tx_...`) |
| `claveIdempotencia` | `String? @unique` | Evita cobros duplicados |
| `errorMensaje`, `metadata` | `String?`, `Json?` | Diagnóstico y trazabilidad |

### `billetera`

| Campo | Uso |
|---|---|
| `saldoDisponible` | Dinero listo para retirar |
| `saldoPendiente` | Dinero retenido mientras una dispersión está en proceso |
| `totalGanado` | Acumulado histórico de ingresos |
| `totalRetirado` | Acumulado histórico de retiros completados |

### `transaccion_billetera`

Libro mayor de la billetera: cada abono, retiro o reverso guarda `tipo`,
`monto`, `saldoDespues`, `estado` y `metadata` (ids de pago, alquiler, payout
y cuenta enmascarada).

### `retiro`

| Campo | Uso |
|---|---|
| `metodo` | NEQUI / DAVIPLATA / BANCO |
| `cuenta` | Celular o cuenta bancaria (se devuelve enmascarada) |
| `monto`, `moneda` | Valor solicitado |
| `estado` | PENDIENTE → PROCESANDO → COMPLETADO / FALLIDO |
| `idPayout` | Id de la dispersión sandbox (`sbx_po_...`) |
| `completadoEn`, `errorMensaje` | Resultado de la dispersión |

### Reservas (`alquiler`)

Ya contempla `subtotal`, `comision`, `total`, `horas`, `inicio`, `fin` y
`estado`. El checkout puede pagar una reserva existente o crearla en el mismo
paso validando disponibilidad y cruces de horario. Al crearla, el servidor
genera un código de devolución y lo entrega al arrendatario una vez aprobado el
pago; el propietario no recibe el código en las consultas de reservas. Para
reservas antiguas pagadas que no tengan código persistido, la consulta del
arrendatario genera y guarda un código nuevo para poder completar la devolución.

## 4. Endpoints

### HU-06 — Pagos

| Método | Ruta | Descripción |
|---|---|---|
| `POST` | `/api/payments/checkout` | Cobra una reserva y reparte la comisión |
| `GET` | `/api/payments/status/:transactionId` | Estado por id de pago o de pasarela |
| `GET` | `/api/payments/history` | Historial de pagos del usuario |

`POST /api/payments/checkout` acepta dos modos:

```json
// A) Pagar una reserva existente
{ "alquilerId": "seed-alquiler-diego-silla" }

// B) Crear y pagar la reserva en un solo paso
{
  "articuloId": "seed-articulo-calculadora",
  "horas": 3,
  "inicio": "2026-10-25T14:00:00.000Z"
}
```

Headers opcionales:

- `x-usuario-id`: identifica al usuario (mientras no exista JWT).
- `Idempotency-Key`: evita cobrar dos veces la misma intención de pago.

Respuesta exitosa:

```json
{
  "exito": true,
  "estado": "COMPLETADO",
  "pagoId": "cm...",
  "transaccionId": "sbx_tx_...",
  "alquilerId": "seed-alquiler-diego-silla",
  "desglose": {
    "subtotal": 24000,
    "comision": 2880,
    "total": 24000,
    "montoPropietario": 21120,
    "porcentajeComision": 0.12
  },
  "mensaje": "Pago aprobado en sandbox..."
}
```

Si la pasarela rechaza, responde **402 Payment Required** con
`codigo`, `mensaje` y el desglose. La reserva queda disponible para reintentar
y el pago se guarda como `FALLIDO`.

### Reservas

| Método | Ruta | Descripción |
|---|---|---|
| `GET` | `/api/reservas` | Reservas del usuario (`rol`, `estado`, `limite`) |
| `GET` | `/api/reservas/:id` | Detalle con artículo, participantes, desglose y pago |
| `POST` | `/api/reservas/articulos/:articuloId/entrega` | Certifica entrega presencial usando QR o PIN |
| `POST` | `/api/reservas/articulos/:articuloId/devolucion` | Confirma la devolución con `{ "codigo": "4821" }` y reactiva el artículo |
| `POST` | `/api/reservas/:id/pagar-mora` | Paga por checkout un recargo que no pudo debitarse de la billetera |

El detalle solo es visible para el arrendatario o el propietario de la reserva.
El desglose (`subtotal`, `comision`, `total`, `montoPropietario`) se calcula en
el servidor, de modo que el frontend no repite reglas de negocio.
El código de devolución solo aparece en las consultas del arrendatario cuando
el pago fue completado; el propietario debe validarlo para cerrar el alquiler.

### RN-10, RN-11 y RN-12 — Entrega, devolución y mora

- La entrega y la devolución requieren certificación presencial del propietario
  con el QR único de la operación o el PIN alternativo de 4 dígitos del
  arrendatario. La lectura de entrega pasa el alquiler a `ACTIVO`; la lectura de
  devolución lo completa.
- Cada minuto, el backend actualiza los alquileres no devueltos. Tras 15 minutos
  de gracia calcula `tarifaHora × ceil(minutos de retraso facturable / 60)`,
  aumenta el recargo al avanzar cada hora o fracción, y marca el alquiler
  `EN_MORA`.
- Al confirmar la devolución, el backend intenta debitar el recargo de la
  billetera del arrendatario. Si el saldo no alcanza, el cargo queda pendiente
  y se paga mediante el endpoint `pagar-mora` (sandbox).
- Si la devolución supera dos horas de retraso, la cuenta se bloquea para
  nuevas reservas. El bloqueo se levanta cuando el artículo está devuelto y el
  recargo está pagado.

### HU-10 — Billetera

| Método | Ruta | Descripción |
|---|---|---|
| `GET` | `/api/wallet/balance` | Saldo disponible, pendiente y totales |
| `GET` | `/api/wallet/historial` | Transacciones (filtro `tipo`, `limite`) |
| `POST` | `/api/wallet/withdraw` | Solicita retiro y ejecuta el payout |
| `GET` | `/api/wallet/withdrawals` | Solicitudes de retiro |
| `GET` | `/api/wallet/entidades` | Métodos de retiro disponibles |

Body de retiro:

```json
{
  "metodo": "NEQUI",
  "cuenta": "3001112233",
  "monto": 50000
}
```

Validaciones:

- Retiro mínimo **$10.000** y máximo **$5.000.000** por operación.
- Nequi/Daviplata: celular colombiano de 10 dígitos que empiece por 3.
- Banco: entre 6 y 20 dígitos.
- El monto no puede superar el saldo disponible.

Flujo del retiro:

1. El monto pasa de `saldoDisponible` a `saldoPendiente` en una operación
   atómica (evita retiros simultáneos que dejen saldo negativo).
2. Se crea la solicitud en estado `PENDIENTE`.
3. Se llama a la pasarela sandbox.
4. Si el payout se procesa: retiro `COMPLETADO`, se descuenta
   `saldoPendiente`, aumenta `totalRetirado` y se registra la transacción.
5. Si el payout falla: se devuelve el dinero a `saldoDisponible`, el retiro
   queda `FALLIDO` y se registra el motivo. Responde **402**.

## 5. Sandbox

`ServicioPasarelaSandbox` simula cobros y dispersiones sin mover dinero real:

- Genera ids `sbx_tx_...` (cobros) y `sbx_po_...` (payouts).
- `SANDBOX_TASA_EXITO` (0 a 1, por defecto `1`) define la tasa de aprobación.
- `SANDBOX_DEMORA_MS` simula latencia de red (por defecto `0`).
- Cualquier DTO de checkout o retiro acepta `forzarFallo: true` para demostrar
  el camino de error de forma determinista.

En producción se reemplaza por un adaptador real (Wompi, Stripe, Mercado Pago)
manteniendo la interfaz `cobrar` / `dispersar`; las dispersiones asíncronas se
confirmarían con webhooks.
